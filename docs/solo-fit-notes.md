# 单人可交付性（Solo Fit）筛选器

> 解决的问题：需求分数回答"哪里痛"，不回答"轮不轮得到我"。
> 这个筛选器按"单人 + AI 辅助"的约束给每条需求打分（0–100）。

## 1. 九个维度

| 维度 | 含义 | 权重 |
|---|---|---|
| third_party_actionable | 第三方能不能介入（根因在厂商应用内 → 1-2） | 20% |
| leverage | 能否真正消除障碍，还是只能监控/提醒 | 15% |
| competition_gap | 是否已被系统自带/免费工具/巨头占满 | 15% |
| software_only | 是否纯软件可解 | 10% |
| zero_onboarding | 装上就用，不需要逐客户配置 | 10% |
| no_docs | 不依赖客户文档/知识库 | 5% |
| low_ops | 不需要 7×24 运维/SLA | 10% |
| frequency | 同一买家的使用频率 | 5% |
| self_serve_pay | 能否自助付费 | 10% |

第一版只评了六个维度，结果把「崩溃闪退」打成 94 分——那是厂商 App 内部的事，第三方根本插不进去。
加上 third_party_actionable / leverage / competition_gap 之后，它掉到 38 分。

## 2. 消费语料（10 条需求）

| 分数 | 需求 | 结论 |
|---|---|---|
| 69 | 识别与诊断准确性低 | 方向可行，准确率是壁垒 |
| 59 | 数据记录与统计不准确 | 高频但竞争激烈，需细分 |
| 56 | 订阅取消与退款不透明 | 杠杆有限，竞争存在 |
| 55 | 设备连接与同步不稳定 | 根因在厂商，只宜做轻量诊断 |
| 54 | 外出远程监控失效 | 依赖设备开放，非纯自助 |
| 51 | 关键提醒与警报不可靠 | 接入碎片化，门槛高 |
| 48 | 更新后功能异常 | 分散，价值有限 |
| 39 | 硬件设备耐用性差 | 根因在厂商 |
| 38 | 核心功能崩溃闪退 | 第三方难介入 |
| 26 | 客服响应慢且售后推诿 | 只能曝光，难成产品 |

**没有一条过 70。** 这和前面两轮人工判断一致：消费语料里没有适合单人的干净机会。

## 3. 开发者工具语料（10 条需求）

| 分数 | 需求 | 短板 |
|---|---|---|
| 82 | 数据导入导出困难 | 低频 |
| 81 | 工具崩溃/卡死无提示 | 竞争（Sentry/系统） |
| 77 | 资源占用高导致卡顿 | 竞争（系统监视器） |
| 74 | 同步/备份状态不透明 | 需接多家云盘 |
| 73 | 插件/扩展兼容性差 | 需维护规则库 |
| 66 | 搜索/导航找不到内容 | 系统搜索已占位 |
| 64 | 跨平台行为不一致 | 杠杆有限 |
| 61 | 权限提示干扰操作 | 只能缓解 |
| 56 | 订阅/付费模式不合理 | 杠杆有限 |
| 33 | 社区发帖被自动删除 | 平台黑箱 |

工具语料的天花板明显更高（82 vs 69），但**高分项都有明显短板**：
数据导入导出低频、崩溃监控有 Sentry、资源监控有系统自带。

## 4. 结论

1. **筛选器的价值在"排除"，不在"选优"**：它把 20 条需求砍到 3–4 条值得认真看的；
2. **没有 90 分的机会**：在"单人 + 买断 + 零支持"约束下，这本身就是常态；
3. **最高分不等于最该做**：82 分的数据导入导出，短板正好是"低频"——和你对退订助手的判断一样。

## 5. 工程

- `src/painradar/solo_fit.py`：九维评分 + 缓存 + 失败兜底
- `python run.py solo-fit --snapshot var/discovery.json --attach`
- 结果写回快照的 `solo_fit` 字段，发现页卡片与抽屉都会显示
- 工具语料单独评分：`--snapshot docs/discovery-devtools/discovery.json --out var/solo_fit_dev.json`
- 测试 5 个（满分/零分/解析/缺维度/失败兜底），**共 120 个全过**

## 6. 局限

- 分数是 LLM 判断，不是测量；同一需求换模型可能差 10 分；
- 没有"个人技能匹配"维度（比如你是否擅长 macOS 开发）；
- 竞争判断靠模型知识，可能过时。
