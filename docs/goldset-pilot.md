## 解读（n=55，含第二批盲标）

| 指标 | 规则（过滤后） | LLM（过滤 + 判定树） |
|---|---|---|
| 有效痛点 P / R / F1 | 89.3% / 67.6% / 76.9% | **91.7% / 89.2% / 90.4%** |
| L 级完全一致 / ±1 | 72.0% / 96.0% | 75.8% / 93.9% |
| 场景一致 | 68.0% | 60.6% |
| 绕行方案 F1 | 20.0% | 58.8% |
| 阻碍可支撑率（跨语言仅参考） | 4.0% | 69.7% |

1. **LLM 的 F1 优势在扩大样本后仍然成立**（90.4% vs 76.9%），且精确率/召回更均衡
   （91.7% / 89.2%），不再靠"全召回"撑数字。
2. **场景一致率是最弱项**：LLM 只有 60.6%，规则反而 68.0%。原因不在模型，在分类体系本身——
   「App 与连接」「固件与更新」「其他场景」三者边界模糊。下一步该合并/加同义词，而不是换模型。
3. **L 级完全一致 75.8%、±1 一致 93.9%**：分歧依旧集中在 L1/L2，判定树把方向固定了，但
   "什么算自救动作"仍需在标注指南里补例子。
4. **规则在绕行方案上有所改善**（0% → 20%），因为判定树给了它一部分 L2 信用，但仍远低于 LLM。
5. **标注本身也被审计出问题**：复核时发现一条保险 App 的评论被误标为有效痛点，
   已修正为品类外。这说明"单标注者 + 无仲裁"确实会引入噪声，双标是必要的。

## 结论

- 默认抽取器用 LLM 有数据支撑；规则保留为离线回退。
- 下一阶段的瓶颈不是抽取，而是**分类体系**（场景）与**标注一致性**（L1/L2 举例）。
- 200 条里已标 55 条，剩余 145 条已切成 4 个批次（`data/goldset/batches/`），拿到第二标注者后先算 α 再合并。

## 场景词表 v2 实验（未采纳）

**假设**：场景一致率低是因为「App 与连接」成了万能桶。v2 去掉 "app" 这个泛词，新增
「广告与推广 / 功能与易用 / 设备硬件 / 账号与数据」，并按"具体 → 泛化"排序。

**做法**：改 `config.scenes`，用确定性 `taxonomy.classify_scene()` 重映射已有原子，
再与同一批 55 条金标比对（只重标了 8 条 其他场景）。

**结果：反而更差。**

| 版本 | 规则场景一致 | LLM 场景一致 |
|---|---|---|
| v1（现状） | 68.0% | 60.6% |
| v2 重映射 | 40.0% | 57.6% |

**原因诊断**：

1. **金标自身不干净**：5 条登录/账号类评论我标成了「App 与连接」，按 v2 定义应属「账号与数据」。
   只重标 8 条、其余 47 条沿用旧标签，等于拿两套标准互相评分。
2. **关键词重映射 ≠ 模型判断**：用 quote 里的关键词重算场景，丢掉了原文上下文；
   而 LLM 是读全文的。两者不可比。
3. **边界本身模糊**：""Unable to connect after update"" 同时命中「连接」和「更新」，
   任何单一排序都会错一半。

**决定**：回退到 v1，场景一致率维持 68.0% / 60.6%。词表迁移不是一次代码改动，
而是一次**标注项目**：定义 v2 → 全量重标 → 更新提示词 → 重跑 LLM → 再评分。
在拿到第二标注者之前做这件事，只会制造新的不一致。

**保留**：`taxonomy.classify_scene()` 作为统一入口（规则抽取器已改用它），
v2 词表与实验记录留在这里，等标注人力到位再启动。
