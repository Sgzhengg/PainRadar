# 从痛点到处方：解决方案生成

> 目标：不止说"哪里有痛"，还要说"做什么能解、谁付钱、两周能做出什么、怎么验证"。
> 结果：为前 3 条需求各生成 3 个方案，每个方案都绑定一条原文证据。

## 1. 怎么保证不是空话

schema 强制每个方案包含：

| 字段 | 作用 |
|---|---|
| evidence_index | 对应第几条原文证据（越界直接丢弃） |
| mechanism | 如何消除那条证据里的障碍 |
| buyer | **必须取自输入的买家分布**，不许新造人群 |
| mvp | 3–5 条，两周内能做完 |
| pricing / price_band | 具体价格数字 |
| why_now | 只能引用给定趋势或证据 |
| validation | 假设 / 实验 / 阈值 / 周期，缺一不可 |
| risks | 至少两条 |

`Solution.valid()` 会拒绝：缺验证四要素、证据索引越界、没有 MVP 的方案。

## 3. 一个方案长什么样

以「HA 连接看门狗」为例（节选）：

```
机制：证据里 Home Assistant 用户反复描述集成掉线、需要重启容器；
      方案是持续探测集成健康度，掉线自动重启集成并记录原因。
对应证据：> ...the integration goes unavailable every few hours...
MVP：健康探测 / 自动重启 / 掉线日志 / 通知
7 天验证：招募 20 名 HA 用户，安装插件 7 天；
          阈值：≥60% 的掉线在 1 分钟内自动恢复
风险：HA 版本兼容性；权限要求高
```

## 4. 必须承认的三个问题

1. **价格币种不对**：语料以美区/全球为主，方案却用人民币定价。
   对海外买家应改成 USD；这是下一版要修的。
2. **方案未经验证**：它们是 LLM 基于证据生成的假设，不是已证明的生意。
   每个方案自带验证实验，但实验还没做。
3. **可行性是自评**：1–5 分由模型给，没有工程评估背书，只能当排序参考。

## 5. 工程

- `src/painradar/solutions.py`：生成、schema 校验、缓存、Markdown 渲染
- `python run.py solve --snapshot var/discovery.json --top 3`
- 输出：`docs/solutions/*.md` + `var/solutions.json`
- 缓存键含需求内容哈希，需求变了会重新生成
- 测试 4 个（合法解析、越界拒绝、缺验证拒绝、渲染包含证据）
- 总测试 **113 个全过**

## 7. 币种已修（USD 默认）

之前方案用人民币给海外买家定价，已修正：

- `run.py solve` 新增 `--currency`，默认 **USD**（语料以美区/全球为主）；
- 币种写进 prompt（"价格一律用 USD 计价"），并进入缓存键，切换币种会重新生成；
- 重新生成后价格变成 `$2.99/月`、`$19.99`、`$9.99` 这类量级；
- 需要国内市场时：`--currency CNY`。

## 10. 方案已收敛：每个需求只推荐一个

生成 3 个方案后，再做一次 LLM 排序（一次调用），标准是"两周内最可能验证出付费意愿"：

| 需求 | 建议先做 | 理由 |
|---|---|---|
| 设备连接 | Home Assistant 连接守护（$19.99） | 可行性最高，买家明确且付费习惯强 |
| 更新后功能异常 | 更新后数据恢复（$9.99） | 数据丢失痛点强，一次性定价易验证 |
| 订阅取消退款 | 取消退款导航（$4.99） | 直接解决取消不透明，实现难度低 |

排序结果写进 `var/solutions.json` 的 `recommended` 字段，同时：

- Markdown 报告顶部加一行「建议先做」；
- 发现页抽屉顶部显示推荐理由，推荐卡片加橙色边框和「建议先做」徽章；
- LLM 排序失败时回退到"可行性最高 + MVP 最少"，并在理由里注明是回退规则。
