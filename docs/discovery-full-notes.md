# 全量 LLM 抽取 + 需求发现：最终结果

> 语料：4 个品类、**3,307 条**评论 → **1,989 个原子** → 44 个簇（31 个唯一标签）
> 抽取：LLM 单遍（`--no-llm-consistency`），耗时 47 分钟
> 发现：两阶段归一化 + 需求打分，需求表 **v2**，31/31 簇全部分配

## 1. 结果

## 2. 买家分布（这次是真的）

```
订阅取消与退款不透明（180 条，跨 3 个域）
- budgeting:       从 Mint 迁移、使用过 PocketGuard 的预算应用用户（91 条）
- pet_water_fountain: 付费订阅用户（86 条）
- plant_care:      植物养护应用用户（3 条）
```

不是占位，是评论里真实出现的人群。第 2 条“提醒不可靠”覆盖睡眠 80 / 宠物 71 / 植物 50。

## 3. 证据强度

| 需求 | L2+ 占比 |
|---|---|
| 订阅取消与退款不透明 | 34% |
| 关键提醒与警报不可靠 | 36% |
| 设备连接与同步不稳定 | **51%** |
| 更新后功能异常 | 17% |

对比规则抽取阶段（8–11%），LLM 抽取把“有绕行/有代价”的证据比例提高到 3–5 倍。

## 4. 与抽样版的对比

`tools/compare_discovery.py` 的输出见 [discovery-diff.md](discovery-diff.md)。

- 抽样版 10 条、全量版 11 条；
- **只有 1 条需求名完全保留**（“更新后功能异常或数据丢失”），其余 9 条因需求表重建而改名，
  在对比工具里表现为“消失 + 新增”。
- 这不是方法失败，而是**标签不稳定**：两阶段归一化每次重建需求表，名称会变。
  真正的稳定性要等需求表被固定下来（人工确认后冻结为 v2，不再自动重建）。

## 5. 结论

- **四条需求跨 3 个域、证据都在 50 条以上**：
  订阅取消 / 提醒不可靠 / 连接不稳定 / 更新后异常。
  这四条可以拿去做访谈，且能直接说清“谁、在哪个域、多少人”。
- **买家分布已经可用**，但只覆盖 4 个品类、App Store 单渠道。
- **需求表名称还不稳定**，跨轮比较必须在同一张表下进行。

## 6. 下一步

1. **冻结需求表 v2**：人工确认 11 条命名后写死，不再自动重建；之后的新数据都归入这张表；
2. **扩品类**：Top Charts 30+ App、10+ 类目，才能回答“哪里最痛”；
3. **加渠道**：Reddit / 论坛 / 众筹，覆盖硬件与线下；
4. 把“发现”页做成默认首页，品类页作为下钻。
