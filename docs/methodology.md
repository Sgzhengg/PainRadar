# 方法论与实现说明

本文解释 PainRadar M1 的实现选择，以及它与《开发方案》各章节的对应关系。目标是让后来者能判断：**哪些是刻意的约束，哪些是临时的妥协。**

---

## 1. 总体链路

```
L0 采集   L1 净化        L2 原子化        L3 聚类        L4 机会化        L5 验证
file/API → 脱敏·去重 → 痛点原子(span) → 语义聚类(canonical 优先) → 评分+市场区间 → 验证包
```

实现位置：

| 层 | 模块 | 说明 |
|---|---|---|
| L0 | `connectors/` | 目前只有 `FileConnector`（BYOD）。官方 API 连接器是 M1 下一批。 |
| L1 | `textproc.py` + `store.find_duplicate` | NFKC 归一、PII 脱敏、MinHash 近似去重。 |
| L2 | `extract.py` | 规则抽取器为主，LLM 抽取器已接线；三道 span 闸（exact/normalized/fuzzy）。 |
| L3 | `cluster.py` | canonical_pain 语义分桶 + 跨桶合并 + 大簇切分；scene 仅兜底；噪声如实统计。 |
| L4 | `scoring.py` + `pipeline.py` | 痛感/机会双分、蒙特卡洛市场区间、机会卡。 |
| L5 | `pipeline.VALIDATION_KIT` | 每张卡固定三个实验与阈值。 |

## 2. 为什么"痛点原子"要带 span

一条评论可以拆成多个断言，但只有**能被原文逐字验证**的断言才配进入评分。做法：

1. 抽取器给出 `quote`；
2. `SpanGate` 在脱敏后的文本里定位，返回 `(start, end, match_score)`；
3. 调用方**重新切片**，用 `text[start:end]` 覆盖模型给的 quote。

因此数据库里的 `quote` 永远等于 `text_masked[span_start:span_end]`，报告里的每条证据都可以被程序回查。测试 `test_end_to_end` 对整批原子做了这个断言。

三种匹配级别：

| 级别 | 触发条件 | 计入发布门 |
|---|---|---|
| exact | 原文直接命中 | 是 |
| normalized | NFKC + 空白折叠后命中 | 是 |
| fuzzy | 首 6 字符锚定 + 窗口相似度 ≥0.90 | 否（只做兜底） |

发布门（方案 §4.3）要求 `exact + normalized` 按「品类 × 平台」各自 ≥95%。M1 尚未实现该看板，`tools/inspect_run.py` 可以先看单次 run 的分布。

### 2.1 LLM 抽取器的四道约束

LLM 只负责"读句子、填槽位"，不负责"下结论"。为此加了四道约束：

| 约束 | 实现 | 失败时 |
|---|---|---|
| 结构化输出 | `response_format=json_object` + 解析容错（裸 JSON / ```json 围栏 / 夹在散文里） | 回退规则 |
| 原文锚定 | 复用 `SpanGate`；quote 失败时依次尝试 `obstacle`、`wtp_quote`；最短 20 字符（中文 12） | 回退规则 |
| 双跑一致性（可选，默认关闭） | `--double-run`：第二次温度 +0.3，比较 level / scene / wtp_level / obstacle 相似度（≥0.6） | 有回退器则回退，否则置信度 ×0.6 并标 `disagree` |
| 枚举收敛 | level 非法则按字段推断；intensity 夹到 1–5；expression/wtp/cost 非法则归一到默认值 | — |

每次结果都会把路径写进 `model_version`：`extract-llm-v0.2|agree`、`|disagree`、
`|fallback-no_span` 等。`stats.extraction` 里能看到 `extracted / fallback / disagree / reasons`，
报告与看板据此判断这一批数据到底有多少是模型给的、多少是规则兜的。

`tools/fake_llm.py` 是一个确定性假端点，用来在不花 token 的情况下跑通整条链路；
它故意只做"取最长句 + 关键词定场景"，所以它的输出质量不代表真实模型。

### 2.2 有效性预过滤

抽取前先判"这是不是一条真痛点"。`validity.py` 用五类信号打分：

```
score = 痛点词(≤3) - 赞美词(≤3, 否定窗口内不计) + 愿望词(≤2)×0.5
        + 求助词×0.5 - 品类外词×2 + 评分先验(≤2星 +1, ≥4星 -0.5)
valid = score > 0
```

- 否定窗口：赞美词前 14 个字符内出现 not/no/never/不/没 等，则不计为赞美。
- 品类外词按品类配置（如宠物饮水机对应 insurance/policy/claim）。
- 结果写进 `stats.validity_filtered`；`--no-validity-filter` 可关闭。

金标 30 条上的表现：P/R/F1 = 90.9%/90.9%/90.9%，优于单独 LLM（89.8%）；
在 200 条上过滤掉 34%，token 成本同比例下降。代价是"功能请求型"抱怨可能被误杀。

## 3. 痛点梯子与"什么算痛点"

判定顺序（`extract._build`）：

```
有购买/付费表达            → L4
有强付费信号，或 有代价+在询价 → L3
有替代方案 或 有明确代价     → L2
只有阻碍                    → L1
什么都没有                  → L0（丢弃）
```

L0 直接丢弃；L1 保留但不会被单独推荐。这样做的代价是召回下降，收益是**每一张机会卡都至少有一个"绕行方案"作为需求存在的证据**——这正是方案里"有痛无市"判断的前提。

### 3.1 判定树与 workaround_type

金标试点显示，L1/L2 的分歧几乎全部落在"有没有采取替代/自救动作"。把这件事交给模型自由判断，
不同调用之间就会漂移。因此改成两步：

1. LLM 只判 `workaround_type`：`none` / `substitute` / `self_rescue` / `escalation`；
2. `levels.resolve_level()` 按固定树计算等级：

```
无阻碍 → L0；已为解决方案付费 → L4；询价/比价/试过 → L3
substitute 或 self_rescue → L2
其余（含仅联系客服）→ L1
```

"联系客服"被刻意排除在绕行方案之外：它是对问题的反应，不是替代方法。规则抽取器用同一棵树，
只是 `workaround_type` 由 `classify_workaround()` 的关键词判定得出。

树的价值不是提高准确率（30 条试点上 ±1 一致率持平），而是让等级**可复现、可审计**，
并且修掉了"买过产品就判 L4"的通胀。

## 4. 聚类：为什么先分场景

短评论的 TF-IDF 向量非常稀疏，直接做全量层次聚类会得到"1 个大簇 + 一堆噪声"（M1 开发中实测如此）。改成两步：

1. 先用受控场景词表把原子分桶（夜间噪音 / 清洗换水 / 水泵故障 / 电源线……）；
2. 桶内 ≥8 条时，再做平均连接层次聚类，把两个不同阻碍拆开；
3. 「其他场景」不硬凑：只在相似度切分成功时成簇，否则计入噪声。

这是**可解释性优先**的妥协：报告能说清"这个簇来自哪个场景"，而 embedding 聚类暂时说不清。代价是跨场景的同一痛点会被切开（例如"噪音"与"电机故障"其实是同一条链），这留到 M2 用 embedding + 人工合并解决。

噪声率会写在报告首屏，不隐藏。

## 5. 评分

### 5.1 痛感

| 因子 | 权重 | 计算 |
|---|---|---|
| 频次 | 0.30 | `log1p(n)` 除以全量最大值 |
| 人群广度 | 0.25 | 去重作者数 / n，再除以最大值 |
| 情绪强度 | 0.20 | 平均 intensity / 5 |
| 代价清晰度 | 0.15 | 有 cost 的原子占比 |
| 持续性 | 0.10 | 评论时间跨度 / 90 天，封顶 1 |

### 5.2 机会

```
Opp = 100 × Π(f_i ^ w_i) / Competition^0.10
```

| 因子 | 权重 | 当前实现 |
|---|---|---|
| Pain | 0.30 | 上式 /100 |
| 供给缺口 | 0.20 | `0.35 + 0.45·替代方案占比 + 0.20·L3/L4 占比` |
| 付费信号 | 0.20 | `0.55·显式付费信号 + 0.45·L3/L4 占比`，按覆盖率向 0.5 收缩 |
| 可服务性 | 0.15 | 默认 0.70（D 级假设） |
| 时机 | 0.15 | 默认 0.65（D 级假设） |
| 竞争 | 0.10（分母） | 默认 0.60（D 级假设） |

**为什么向 0.5 收缩**：如果 100 条评论里没有一个人说"我愿意付钱"，正确的结论是"没观测到"，不是"付费意愿为 0"。几何平均会把 0.02 放大成灾难性惩罚。收缩公式：

```
wtp = 0.5 + (raw_wtp − 0.5) × min(1, coverage × 2)
```

`coverage` 同时写进因子表（`付费信号覆盖率`），报告里明确提示"不应解读为没有付费意愿"。

### 5.3 分档

初始阈值：强 ≥60，中 ≥42。**必须在看数前预注册**，之后只能按季度回测校准——否则阈值会被事后调参污染（评审纪要 §12.6 算法负责人的保留条件）。

## 6. 市场区间

自下而上五因子：

```
SOM = 人群 × 渗透率 × 可触达率 × 年转化率 × 客单价
```

每个因子是 `(low, mid, high)` 三角分布，蒙特卡洛 2 万次（固定种子 42），取 P10/P50/P90。

**为什么不用 low×low×…**：五个因子各取低值，等于假设五个独立事件同时发生，会得到跨两个数量级的区间，客户无法据此决策。蒙特卡洛给出的是联合分布的分位数。

每个假设带来源等级（A 一手 / B 第三方 / C 评论推断 / D 类比），并输出：

- 敏感性排序（把单个因子推到高/低值时，中值变化多少）；
- **证伪条件**（转化率或客单价低于某阈值则区间作废）。

簇级市场 = 品类 SOM × 声量份额（簇原子数 / 总原子数），份额本身标为 C 级假设。这是 M1 的近似；M2 应改为按人群校准。

## 7. 证据台账

表结构见 `store.SCHEMA`。关键约束：

- `atoms` / `scores` / `opportunities` 只插入，不更新；
- 每条派生行带 `run_id`、`model_version`、`prompt_version`、`taxonomy_version`；
- 删除请求走 `soft_delete`：评论置 `deleted_at`，派生原子物理删除，并写审计日志；
- `audit` 表记录导入、删除等动作。

`runs` 表保存每次运行的统计快照，报告以 `run_id` 为锚，可复现。

## 8. 评测：A 集金标

方案要求两套集：A 集（抽取质量）与 B 集（结局回测）。当前完成的是 A 集的第一版：

- 语料：3 个宠物设备 App、632 条真实评论（`var/gold.db`）。
- 抽样：按「评分档 × 规则抽取结果」分层，抽 200 条；`tools/make_goldset.py` 输出标注表与 30 条盲标试点。
- 标注：`docs/annotation-guide.md` 定义 L0–L4、场景词表与判定树；已盲标 55 条（30 + 25）。
- 评分：`tools/score_goldset.py` 输出有效痛点 P/R/F1、L 级一致率与 kappa、场景一致率、绕行方案 F1；
  `tools/alpha.py` 用于双标注者的 κ/α；`tools/labels_merge.py` 合并批次。
- 结果（n=55）：LLM 有效痛点 F1 90.4% vs 规则 76.9%；L 级 ±1 一致 93.9%；绕行方案 F1 58.8% vs 20%。
- 最弱项是**场景一致率**（LLM 60.6%、规则 68.0%），问题在分类体系边界，不在模型。
- 场景词表 v2 实验失败并回退：只重标 8/55 条就重映射，等于两套标准互相评分；
  词表迁移必须先全量重标、再更新提示词、再重跑，否则数字只会更差。

### 8.1 B 集：结局回测

A 集回答"抽得准不准"，B 集回答"预测有没有用"。实现方式是一次**时间切分**：

```
只用 T0 之前的评论 → 聚类 → 生成预测（簇 + 关键词 + 12 个月窗口）
                                          ↓
                  GitHub 新仓库（≥5 stars，命中 ≥2 个关键词）
                  App Store 新上架应用（releaseDate 在窗口内）
                                          ↓
                             命中率 vs 随机关键词基线
```

- 预测单元：`(cluster, T0, keywords)` → "T0 起 12 个月内是否出现针对该痛点的付费产品"。
- 关键词来自原子 quote 的英文词（去掉 app/device/pet 这类泛词），不是中文场景名，
  否则 GitHub / App Store 搜不到。
- 基线：从**同一语料词表**随机抽同样数量的词，跑同样的查询。
  两者接近说明关键词没有区分度，而不是"系统有效"。
- 命中只是"出现了相关产品"，不等于"这个产品成功了"；它是**证伪**工具，不是成功预测器。

已知盲区：GitHub 与 App Store 覆盖不到硬件众筹、线下服务、B 端采购；
关键词可能带噪声；T0 前样本小。结论只能做方向性判断。

**第一次实测的教训**（见 `docs/backtest.md`）：随机词组的命中率是 90%，
预测是 25%——命中门槛太松，词面匹配几乎必然成立。这说明**结局判定本身才是瓶颈**，
不是模型。下一步必须先做语义裁决与人工抽检，再谈命中率；否则每次调参都会得到不同的"结论"。

**第三次实测**：按 App 拆分（6 个应用、307 条训练数据、9 簇）得到 5 个合格预测，
命中 2/5 vs 随机基线 4/6。证据质量已经可信（SubSeek/Submo 对应取消订阅难、Popur S7 对应自清洁猫砂盆），
但基线仍然太容易命中，lift 无意义。

**稳定结论**：B 集当前"证据可信、统计不可用"。要可用，需要 30+ 预测、可比的基线
（随机品类主题，而不是随机 bigram）以及预注册的判定规则。在此之前不对外发布命中率。

### 8.2 前向测试

回测无论怎么做都存在事后选择的空间，因此对 `plant_care` 登记了前向测试：

- `forward_register.py` 用今天的语料生成 3 条品类内预测 + 6 组随机基线，
  写入 `predictions` 表（`mode='forward'/'baseline'`），窗口固定 12 个月；
- 判定规则写进 `docs/forward-protocol.md`，登记后不得修改；
- `forward_check.py` 在窗口结束前拒绝运行（返回码 2），到期后才采集结局；
- 成功判据预注册为"命中率 ≥ 基线 + 20pp 且至少 3 条命中"，样本小只作方向性判断。

这比再跑十次回测更有价值：它把"系统能不能预测"变成一个**未来才会揭晓、且无法篡改**的问题。

仍然缺的：200 条全量标注、第二标注者与逐字段 α、以及 B 集（≥150 个预测单元、≥50 个结局）。
没有 B 集之前，"预测市场空间"只能算假设，不能对外承诺。

评分指标的两个坑，已在报告里注明：

1. **kappa 对偏斜分布不敏感**：样本 73% 是 L1，kappa 只有 0.33/-0.06，但 ±1 一致率 95.5%——应以前者为主、后者为辅。
2. **阻碍支撑率跨语言不可比**：规则输出英文、金标是中文，bigram containment 天然接近 0；该指标只适合同语言比较。

## 10. 数据源与外部锚

### 10.1 连接器

| 源 | 认证 | 速率 | 产出 |
|---|---|---|---|
| App Store RSS | 无 | 0.5 req/s | 每条评论一个 item（标题+正文、评分、日期、链接） |
| Reddit | OAuth（推荐）或公开 JSON | 1.2 / 0.2 req/s | 帖子 + 一级评论，各自成为 item |
| 文件/BYOD | 无 | — | JSONL/JSON/CSV |

设计要点：

- **登录态零依赖**：两个连接器都不使用用户 Cookie，也不做签名逆推。Reddit 走官方 OAuth；App Store 走公开 RSS。
- **速率与重试**：`net.RateLimiter` 令牌桶 + 指数退避 + `Retry-After`；429/5xx 自动重试，4xx 直接失败。
- **可测**：`HttpClient(transport=...)` 允许注入假传输，27 个测试全部离线。
- **文本与证据分离**：连接器只产出 `RawItem`，脱敏、去重、入库由 `pipeline.ingest_items` 统一处理。

### 10.2 Amazon 的现实约束

Amazon PA-API 不返回评论正文，抓取评论违反 ToS。因此本项目的 Amazon 侧定位是**只做锚**（价格、BSR、评分人数），评论文本走 BYOD（卖家后台导出）或持牌数据商。这不是偷懒，是合规约束下的唯一路径。

### 10.3 外部锚

锚是"评论之外的事实"，用来回答两个问题：样本覆盖了多少人群？市场假设是否离谱？

- `ItunesAnchor`：公开 lookup API，拿 `rating_count` / `avg_rating`，等级 A。
- `import_csv`：导入 Keepa / Ad Library / 人工调研的 `price` / `bsr` / `ad_count`，等级按来源标注。
- 报告 §3 展示锚，并计算**样本覆盖率** = 本次扫描条数 / 锚定评论总量。覆盖率 0.1% 时，任何结论都只能当假设。

锚的第二个用途是校准市场假设（M1-c）：例如用 `rating_count × 评论率` 反推活跃用户量，替换当前 C 级的"目标人群规模"。这一步尚未自动化。

## 11. 与开发方案的偏差记录

| 方案 | 实现 | 原因 |
|---|---|---|
| HDBSCAN 聚类 | canonical 语义分桶 + 跨桶合并 + 平均连接 | 短文本上 HDBSCAN 噪声率过高，先保证可解释 |
| LLM 抽取为主 | 已实现，但默认仍用规则 | 规则离线可跑、可测试；LLM 需端点与预算，按品类开启 |
